# План натурного тестирования прошивки POWER_Controller (STM32F030R8T6)

Документ описывает **полный цикл проверки на реальном железе** для контроллера питания MCU. Нормативные требования к поведению, протоколу UART, GPIO, секвенсингу и защитам зафиксированы в:

- `POWER_Controller.md` — основная спецификация прошивки и железа;
- `README.md` — роли, UART и операционные сценарии хоста;
- `Config/config.h` — численные константы (таймауты, пороги, длины пакетов).

Инструменты (полный цикл): **мультиметр**, **логический анализатор**, **USB-UART** (UART0 и при необходимости UART_Debug — только **TTL 3.3V**, не «настоящий» RS-232 ±12V).

### Минимальный стенд

Если проверяете плату на столе без полной системы, достаточно:

| Обязательно                                                                                    | Зачем                                 |
| ---------------------------------------------------------------------------------------------- | ------------------------------------- |
| Питание платы по схеме ревизии + **общий GND** со всеми приборами                              | безопасный старт и измерения          |
| **SWD-программатор**                                                                           | прошивка, `NRST`                      |
| **USB-UART 3.3 В** на **UART0** (`PA9` TX MCU → RX адаптера, `PA10` RX ← TX адаптера, **GND**) | протокол с ПК                         |
| **Мультиметр**                                                                                 | этап A, контроль шин по необходимости |

Желательно по мере задач: **логический анализатор** (UART, Enables, `PWRBTN#`, PWM). Второй UART (**UART_Debug** `PA2`/`PA3`), развёрнутые замеры всех точек АЦП — опционально; см. [§4](#4-подключение-оборудования-что-куда).

**Краткий порядок:** минимум **A → B → C**; дальше по возможности **E**, **D**, **H**, **K**, **J**; **F**, **G**, вход в bootloader (**§13**) — когда доступно железо и время.

## 1. Цели натурных испытаний

1. Подтвердить корректный **bring-up** MCU (питание, тактирование, старт после прошивки).
2. Проверить **UART0** с хостом (эмулятор master на ПК): формат кадра, CRC, таймауты, все команды и инварианты политики.
3. Проверить **GPIO доменов**, **PWM подсветки**, **power sequencing дисплея** и **аудио-секвенс** усилителя по времени и уровням.
4. Проверить **мониторинг АЦП** (напряжения шин, токи, входы `PGOOD` / `Faultz` / `IN_0…IN_5` / `SUS_S3#`) и срабатывание **fault + safe state + latch**.
5. Проверить сценарии **восстановления после fault**, **RESET_BRIDGE**, **BOOTLOADER_ENTER**, **CALIBRATE_OFFSET** (flash).
6. Проверить **IWDG** (отсутствие ложных reset при нормальной работе; срабатывание при зависании main loop).
7. Зафиксировать стабильность на **длительном прогоне**.

MCU **не шлёт асинхронных событий** на хост: состояние и fault выясняются по **`GET_STATUS`** и ACK/NACK команд (`README.md`, `POWER_Controller.md`).

## 3. Безопасность и ограничения

- Работы на **живых шинах 12/24 В** и силовых цепях — только при отключении питания или с использованием измерений, допустимых схемой; не создавать КЗ на измерительных точках АЦП.
- **VDDA = 2.5 В** (IC9): при сравнении телеметрии с мультиметром помнить, что расчёт мВ в прошивке завязан на **опору 2.5 В**, не 3.3 В (`POWER_Controller.md` §2.4, `config.h`).
- Токовые каналы NSM2012: при сильной нагрузке возможен **клиппинг АЦП** (~3.2 A без искажений) — это норма измерительного тракта, не обязательно «баг» (`POWER_Controller.md` §2.4, §19.1).
- Команда **`CALIBRATE_OFFSET`** — **запись во flash** (износ страницы); выполнять редко, на гарантированно нулевой нагрузке по токовым каналам.

## 4. Подключение оборудования: что куда

**Общая земля** обязательна для USB-UART, LA и программатора.

Расположение тест-падов и разъёмов — по **`MCU.SchDoc`** / BOM / ревизии; ниже — **сигнал ↔ пин MCU** из `POWER_Controller.md` (приложение GPIO).

### 4.1 Уровни и тип адаптера UART

- Нужен адаптер **USB ↔ TTL UART 3.3 В** (иногда маркируют «3V3 CMOS UART»).
- Классический **USB-RS232** с разъёмом DB9 обычно выдаёт **±12 В** — **не подключать** напрямую к `PA9`/`PA10`/`PA2`/`PA3`. Если только такой адаптер — использовать преобразователь уровней RS-232 ↔ 3.3 В TTL или заменить модуль.

Пины MCU **не терпят 5 В TTL** без защиты — держите **3.3 В**.

### 4.2 Программатор / отладчик по SWD

Подключение к STM32 F0 (типовая распиновка на плате или коннектор SWD):

| Сигнал программатора             | Куда на MCU / плате             | Примечание                                                                |
| -------------------------------- | ------------------------------- | ------------------------------------------------------------------------- |
| **SWDIO**                        | `PA13`                          | данные SWD                                                                |
| **SWCLK**                        | `PA14`                          | такт SWD                                                                  |
| **GND**                          | **GND платы**                   | обязательно                                                               |
| **3V3** (VTref / target voltage) | **`+3.3V_A`** / `VMCU` по схеме | нужно программаторам, которые определяют уровень интерфейса по опоре цели |
| **RESET / NRST**                 | вывод **`NRST`** MCU            | желательно; упрощает вход под отладчик                                    |

Не подключайте **5 В** от программатора на линии **3.3 В** цели.

После прошивки SWD можно не отключать.

### 4.3 UART0 — связь с хостом (эмуляция master с ПК)

Параметры линии: **115200 8N1**, без RTS/CTS (`README.md`, `POWER_Controller.md` §3.1).

На стороне **микроконтроллера** (истина для разводки):

| Роль линии UART | Пин MCU    | Направление данных                          |
| --------------- | ---------- | ------------------------------------------- |
| **USART TX**    | **`PA9`**  | **MCU → хост** (ответы, телеметрия в кадре) |
| **USART RX**    | **`PA10`** | **Хост → MCU** (команды)                    |

На разъёме / silk часто используют имена **`UART0_RX` / `UART0_TX` со стороны внешнего устройства** — это **перекрёстно** относительно пинов MCU:

| Имя на разъёме (сторона внешнего устройства / «кабеля») | Физически соединено с пином MCU | Подключение USB-UART (TTL 3.3 В)                      |
| ------------------------------------------------------- | ------------------------------- | ----------------------------------------------------- |
| **`UART0_RX`** (хочет принять байты **от MCU**)         | к **`PA9`** (TX MCU)            | **`RX`** адаптера ← точка **`UART0_RX`** / **`PA9`**  |
| **`UART0_TX`** (отдаёт байты **в MCU**)                 | к **`PA10`** (RX MCU)           | **`TX`** адаптера → точка **`UART0_TX`** / **`PA10`** |
| —                                                       | —                               | **`GND`** адаптера ↔ **GND платы**                    |

Если байты не ходят — один раз поменять местами RX/TX на адаптере и повторить **`PING`**. Короткий общий **GND** между платой и адаптером предпочтительнее длинных «висящих» проводов.

### 4.4 UART_Debug (опционально)

Второй USB-UART (TTL 3.3 В): MCU TX **`PA2`** → RX адаптера; MCU RX **`PA3`** ← TX адаптера; **GND**. Скорость и включение в сборке — по CubeMX/`usart.c`. Не путать с UART0 (`PA9`/`PA10`).

### 4.5 Логический анализатор

На минимальном стенде можно обойтись декодированием UART на **`PA9`** в терминале; LA упрощает тайминги GPIO и двусторонний UART.

Подключение каналов (общий **`GND`** с платой):

| Что проверяете             | Куда щуп LA                                                  | Комментарий                                       |
| -------------------------- | ------------------------------------------------------------ | ------------------------------------------------- |
| Обмен UART0                | **`PA9`** (или линия после буфера к разъёму)                 | декодер **UART 115200 8N1**, полярность как у MCU |
| Обмен UART0 (вторая точка) | **`PA10`**                                                   | полезно видеть запрос и ответ одновременно        |
| PWM подсветки              | **`PB9`** (`BL_PWM`, TIM17)                                  | частота/скважность vs `SET_BRIGHTNESS`            |
| Импульс PWRBTN             | **`PC14`** (`PWRBTN#`, open-drain)                           | активное **LOW**                                  |
| SUS_S3#                    | **`PC15`**                                                   | уровень для авто-PWRBTN                           |
| Enable доменов             | **`PB5`** SCALER, **`PB4`** LCD, **`PA15`** BACKLIGHT и т.д. | по таблице GPIO в документе                       |
| Сброс моста                | **`PB8`** (`RST_CH7511b`)                                    | LOW = reset                                       |

Не превышать допустимое напряжение входа канала LA.

### 4.6 Мультиметр

| Измерение                | Где                                                 | Ожидание (ориентир)                                 |
| ------------------------ | --------------------------------------------------- | --------------------------------------------------- |
| Питание MCU              | **`+3.3V_A`** к GND                                 | ~**3.3 В**                                          |
| VDDA                     | **`VDDA`** к GND                                    | ~**2.5 В**                                          |
| Шины **24 / 12 / 5 В**   | цепи **`V+24`**, **`+12V_A`**, **`+5V_A`** по схеме | сравнить с полями `v24`, `v12`, `v5` в `GET_STATUS` |
| Целостность линий вводов | **`PGOOD`**, **`SUS_S3#`** относительно GND         | HIGH/LOW по состоянию системы                       |

Ток через домены при необходимости — **амперметр последовательно** в разрыв допустимого места или клеммы источника стенда (не разрывать шины без понимания обратного тока и защиты).

### 4.7 Конфигурация ПК для UART

- Открыть порт терминала или утилиты на **`115200`**, **`8` бит данных**, **без паритета**, **`1` стоп-бит**, **без аппаратного flow-control**.
- В Linux устройство вида `/dev/ttyS*` или `/dev/ttyUSB*` зависит от адаптера; важно попасть именно в **`UART0`** разводки к MCU.

### 4.8 Протокол (напоминание после подключения)

Кадр: `[STX=0x02][CMD][LEN][DATA…][CRC8][ETX=0x03]`; CRC8/ATM poly `0x07`, init `0x00` по `[CMD][LEN][DATA]`; LE для многобайтовых полей (`POWER_Controller.md` §9).

Таймауты приёма на MCU (`config.h`): **межбайтовый 10 мс**, **пакет 50 мс** — натурные проверки **C.18–C.20** (§7.4).

После reset MCU готов к приёму **не позднее ~100 мс**; до первого успешного обмена допустимы таймауты — синхронизация через **`PING`** (`README.md`).

### 4.9 Сборка прошивки

В корне репозитория: **`make`** → артефакты в **`build/`** (`Makefile`).

### 4.10 Аппаратный вход в ROM bootloader (если есть доступ к `BOOT0` / `NRST`)

Это полезно при проверке прошивки по UART без работающего приложения (`POWER_Controller.md` §1.2):

1. **`BOOT0`** MCU перевести в **HIGH** (перемычка, кнопка или тестовая точка по документации ревизии платы).
2. Подать импульс или аппаратный сброс на **`NRST`**.
3. После входа в bootloader связь — по **тому же UART**, что и приложение (**115200** и протокол ROM UART bootloader STM32 — по RM0091 для семейства).

В штатном режиме **`BOOT0`** должен быть **LOW** (на стороне схемы указан подтягивающий резистор к GND).

| --- | ------------------------------- | ---------------------------------- | ------------------------------------ |

## 6. Этап B — прошивка и базовый bring-up

| ID  | Проверка                             | Метод                                                                                 | Ожидание                                                                                                            |
| --- | ------------------------------------ | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| B.1 | Загрузка прошивки по SWD             | OpenOCD/STM32CubeProgrammer/IDE                                                       | Запись без ошибок, верификация OK                                                                                   |
| B.2 | Старт после power-on                 | 10× cold boot, 10× `NRST`                                                             | Нет зависаний; предсказуемое поведение GPIO safe state                                                              |
| B.3 | Время готовности UART0               | Хост по UART0 (при необходимости LA для тайминга): первый успешный `PING` после reset | В пределах ожиданий README (~100 мс порядок, уточнить натурно)                                                      |
| B.4 | Старт при принудительном `PGOOD=LOW` | Включить питание платы при удержании `PGOOD` в LOW (безопасный способ для стенда)     | Через **≤5 с** (`PGOOD_TIMEOUT_MS`) — `GET_STATUS.fault_flags` содержит `FAULT_PGOOD_LOST`; домены OFF (safe state) |
| B.5 | Восстановление `PGOOD` после B.4     | Подать `PGOOD=HIGH` **без** reset MCU                                                 | MCU **не** запускает секвенс автоматически; ждёт явного `POWER_CTRL` для включения доменов                          |

**Примечание по старту:** после Reset MCU переводит домены в **safe OFF**, ждёт **`PGOOD = HIGH`** до **5 с** (`PGOOD_TIMEOUT_MS`), иначе **`FAULT_PGOOD_LOST`** и остаётся в INIT (`POWER_Controller.md` §6.1, `config.h`). B.4/B.5 проверяют этот сценарий явно (без Q7).

## 7. Этап C — UART0: протокол и инварианты

Использовать скрипт/утилиту на ПК с корректным CRC.

### 7.1 Базовый обмен

| ID  | Сценарий             | Ожидание                                                                          |
| --- | -------------------- | --------------------------------------------------------------------------------- |
| C.1 | `PING (0x01)`        | Ответ `DATA[0] = 0xAA`, `status` как в контракте                                  |
| C.2 | `GET_STATUS (0x04)`  | `LEN(DATA) = 26`; поля по offset (`POWER_Controller.md` §9 GET_STATUS); CRC верен |
| C.3 | Неверный CRC         | Кадр игнорируется; ответа нет или поведение по спецификации                       |
| C.4 | Неизвестный CMD      | NACK `CMD=0xFF` с `error_code` или отсутствие ответа (см. README/§9)              |
| C.5 | Флуд команд (stress) | При перегрузе очереди — `error_code` queue overflow (`0x02`) по контракту         |

### 7.2 POWER_CTRL (0x02) и политика BACKLIGHT

| ID   | Сценарий                                                                              | Ожидание                                                                                                                                                              |
| ---- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C.6  | После нормального старта: прочитать `state`                                           | См. **C.6a** (конкретная маска битов)                                                                                                                                 |
| C.6a | После успешного auto-startup (`PGOOD=HIGH`): `GET_STATUS.state`                       | `SCALER=1`, `LCD=1`, `BACKLIGHT=0`, `TOUCH=1`, `AUDIO=1` — биты **0, 1, 3, 6** = 1; бит **2** = 0 → **`state = 0x4B`** (`POWER_Controller.md` §6.1, таблица битов §9) |
| C.7  | `BACKLIGHT=ON` при выключенных SCALER/LCD (сформировать состояние выключения доменов) | `status=0x01`, **состояние не меняется**                                                                                                                              |
| C.8  | `LCD=ON` без `SCALER`                                                                 | `status=0x01` (`POWER_Controller.md` §13.7)                                                                                                                           |
| C.9  | Включить только BACKLIGHT при валидных SCALER+LCD                                     | `status=0x00`; далее проверить GPIO/PWM (этап E)                                                                                                                      |
| C.16 | `mask=SCALER\|BACKLIGHT`, `value=SCALER ON + BACKLIGHT ON` при **выключенном LCD**    | `status=0x01`; **SCALER остаётся OFF** (команда отклонена целиком, без частичного применения; `README.md`, атомарность `POWER_CTRL`)                                  |
| C.17 | Повторный `GET_STATUS` после C.16                                                     | `state` **не изменился** относительно состояния до команды C.16                                                                                                       |

### 7.3 Остальные команды

| ID   | Команда                 | Ожидание                                                                                                                                                                                                                                                                                                                                                                     |
| ---- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C.10 | `SET_BRIGHTNESS` 0…1000 | `status=0x00`; PWM соответствует (этап E); полярность **не инвертирована** (`POWER_Controller.md` §9 SET_BRIGHTNESS)                                                                                                                                                                                                                                                         |
| C.11 | `RESET_FAULT`           | Только сброс `fault_flags`; **домены сами не включаются**                                                                                                                                                                                                                                                                                                                    |
| C.12 | `RESET_BRIDGE`          | ACK `status=0x00`, импульс `RST_CH7511b` **10 мс** LOW (**выполняется в любом состоянии доменов**; MCU не обязан отклонять по `status=0x01`). **Операционная рекомендация** (`POWER_Controller.md` §13.4): выполнять при **SCALER+LCD ON** — на стенде дополнительно проверить: при выключенном LCD команда **не** возвращает `status=0x01`, импульс на `PB8` всё равно есть |
| C.13 | `SET_THRESHOLDS`        | Валидный `mask` → `0x00`; известные запреты валидации → `0x01` (`POWER_Controller.md` §9)                                                                                                                                                                                                                                                                                    |
| C.14 | `BOOTLOADER_ENTER`      | ACK `0x00`, затем reset и сессия ROM bootloader на UART0 (`POWER_Controller.md` §19.5) — см. раздел **«13. Этап I»** ниже                                                                                                                                                                                                                                                    |
| C.15 | `CALIBRATE_OFFSET`      | `0x00` при нулевой нагрузке; повторное чтение токовых нулей согласовано с flash (§11)                                                                                                                                                                                                                                                                                        |

### 7.4 Таймауты UART и ресинк STX

Константы (`config.h`): `UART_INTERBYTE_TIMEOUT_MS = 10`, `UART_PACKET_TIMEOUT_MS = 50`. Поведение фрейминга — `POWER_Controller.md` §9 (фрейминг и обработка ошибок).

| ID   | Сценарий                                                                                           | Ожидание                                                                         |
| ---- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| C.18 | Отправить `STX + CMD + LEN` (начало кадра, без завершения), пауза **60 мс**, затем валидный `PING` | Первый неполный кадр отброшен (packet timeout); `PING` получает корректный ответ |
| C.19 | Отправить байты валидного кадра с паузой **15 мс** между байтами (> межбайтового таймаута)         | Пакет отброшен; следующий валидный кадр обрабатывается нормально                 |
| C.20 | Отправить `02 04 00` (начало `GET_STATUS`), затем сразу `02 01 00 15 03` (валидный `PING`)         | MCU отвечает на `PING` — ресинх по `STX` в потоке (`POWER_Controller.md` §9)     |

## 8. Этап D — дискретные входы и SUS_S3# / PWRBTN#

### 8.1 Поле `inputs` в GET_STATUS

Распаковка (`README.md`, `POWER_Controller.md`):

- `bit0…5` — `IN_0…IN_5`;
- `bit6` — `PGOOD` (1 = HIGH);
- `bit7` — `Faultz` (1 = HIGH = **нет** fault усилителя; сигнал active LOW на железе — проверить согласованность с платой).

| ID  | Проверка                      | Метод                                                  | Ожидание                                                                                                        |
| --- | ----------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |

## 12. Этап H — инжекция fault и восстановление

Политика (`POWER_Controller.md` §19.4):

- при fault: **`power_safe_state()`**, все домены OFF, усилитель safe, PWM=0;
- **`fault_flags` защёлка** до `RESET_FAULT`;
- **`RESET_FAULT` не включает** нагрузки.

Примеры провокаций (только безопасные для стенда):

| ID  | Провокация                            | Ожидание                                                                |
| --- | ------------------------------------- | ----------------------------------------------------------------------- |
| H.1 | Временный вывод `V24/V12/…` за пороги | После фильтра — соответствующий `FAULT_V*_RANGE`                        |
| H.2 | Превышение тока канала                | `FAULT_LCD` / `FAULT_BACKLIGHT` / …                                     |
| H.3 | Падение `PGOOD` во время секвенса     | `FAULT_SEQ_ABORT` и аварийное выключение по `POWER_Controller.md` §13.1 |
| H.4 | Восстановление                        | `GET_STATUS` → `RESET_FAULT` → явный `POWER_CTRL`                       |

**Assertion для H.1–H.3** (после любого fault-события, в том же или следующем `GET_STATUS`):

```text
assert (fault_flags & 0x8000) == 0   /* FAULT_RESERVED, бит 15 всегда 0 */
```

## 13. Этап I — bootloader и аппаратный вход

### 13.1 `BOOTLOADER_ENTER (0x08)`

Ожидание: ACK, затем переход в ROM bootloader (**`0x1FFFD800`** на APM32 / `0x1FFFEC00` на STM32) на **UART0** (`config.h` `ROM_BOOTLOADER_ADDR`, `POWER_Controller.md` §19.5).

Проверка (без Q7, только PC + USB-UART):

1. Отправить `BOOTLOADER_ENTER` по протоколу приложения; дождаться ACK и обрыва/смены режима на линии.
2. Переключить хост в режим **STM32 USART ROM bootloader** (тот же порт, **115200 8N1**).
3. Минимальная проверка ответа ROM (Linux, порт подставить свой):

```bash
stm32flash -b 115200 /dev/ttyUSB0
```

Ожидание: утилита определяет чип (например STM32F030) и выводит информацию о flash — признак, что ROM-загрузчик отвечает. Альтернатива: **STM32CubeProgrammer** → UART, Connect.

Полная перепрошивка через ROM — опционально; для gate достаточно успешного handshake.

### 13.2 Аппаратный вход (дополнение к п. 4.10)

При недоступности `BOOTLOADER_ENTER`: `BOOT0=HIGH` → импульс `NRST` → тот же `stm32flash`/CubeProgrammer на UART0.

## Общие правила

1. **Чёрный щуп → GND платы** (общая земля с USB-UART, программатором).
2. **Красный → тест-пад / конденсатор / вывод** с нужной надписью (`+3.3V_A`, `VDDA`, `V+24` и т.д.).
3. Режим **DC V** для напряжений; **Ω** только при **обесточенной** плате (проверка КЗ).
4. **Не тыкать в точки АЦП** (делители, `*_POWER_M`) на живых 12/24 В — риск КЗ; шины 12/24 В меряйте на **силовых** узлах схемы.
5. Телеметрия в прошивке считает **VDDA = 2.5 В**, не 3.3 В — при сравнении с `GET_STATUS` закладывайте **±10%** и делители.

## Что проверить прямо сейчас (самое важное)

### 1) Состояние загрузки MCU

- **`NRST` (ножка NRST)**: должно быть около `3.3V`.
- **`BOOT0`**: должно быть `0V` (LOW), чтобы стартовать из Flash.

Если `BOOT0` высокий или `NRST` залип низко — прошивка не пойдет, все ваши GPIO останутся «нулевые/неактивные».

---

### 2) Питания самого MCU

- `+3.3V_A` (VDD MCU): `~3.3V`
- `VDDA` (аналог, у вас 2.5V): `~2.5V`

Если нет 2.5V на VDDA, АЦП/логика fault может вести себя некорректно.

---

### 3) Быстрый признак «код вообще жив»

Подключить USB-UART к `PA9/PA10` и отправить `PING`.

- Есть ответ — код крутится, тогда ищем fault/пороги.
- Нет ответа — MCU не в приложении (BOOT0/NRST/питание/старт).

---

## Почему думаю про BOOT0/NRST

В вашем логе прошивки есть:

- `WARN ... NRST is not connected`

Это не мешает записать flash, но повышает шанс, что после записи МК не перешел в нормальный старт так, как вы ожидаете (особенно если внешняя логика на плате держит `BOOT0/NRST`).

---

## Короткий план на 5 минут

1. Меряем `NRST` и `BOOT0`.
2. Если `BOOT0 != 0V` — принудительно подтянуть к GND и сделать reset.
3. После reset снова смотрим `PB2` и `PC9` через 0.5с.
4. Если всё ещё 0 — проверяем `+3.3V_A` и `VDDA=2.5V`.
5. Потом `PING` по UART.

Если скинете 4 напряжения (`NRST`, `BOOT0`, `+3.3V_A`, `VDDA`), сразу скажу следующий точный шаг.

## Что осталось на голой плате (без дисплея и Q7)

### 1. **B.4 / B.5 — PGOOD** (самое полезное из оставшегося)

- **B.4:** старт при удержании **PGOOD LOW** → в течение ~5 с `fault_flags` с **`FAULT_PGOOD_LOST`**, домены OFF.
- **B.5:** вернуть **PGOOD HIGH** без reset MCU → fault снимается только **`RESET_FAULT`**, нагрузки **сами не включаются**.

После проверки: `make test-uart-reset` или `./Tests_UART/03_reset_fault.sh`.

### 2. **E.1 / E.6** — GPIO (по желанию)

- Щуп/LA: при `state=0` выходы доменов **LOW** (safe state).
- На **`PB8`**: импульс ~10 ms LOW по `RESET_BRIDGE` (скрипт уже PASS по ACK).

### 3. **I — bootloader** (перед релизом прошивки)

`BOOTLOADER_ENTER` или `BOOT0`+`NRST`, затем `stm32flash -b 115200 /dev/ttyUSB0`.

### 4. **J.1** — длительный прогон (опционально)

Периодический `GET_STATUS` 1–8+ ч — стабильность без Q7/дисплея.

### 5. **Отложить**

- **CALIBRATE_OFFSET** — когда будет нулевая нагрузка по токам и готовность писать во flash.
- **C.6a, E.2–E.4, SET_BRIGHTNESS, D (SUS_S3/PWRBTN), F** — с дисплеем и/или Q7.

## Итог по голой плате

Для **минимального стенда** (питание + SWD + UART + мультиметр) вы уже прошли основной gate: **протокол, safe state, телеметрия шин, ожидаемый SEQ_ABORT без дисплея, сброс fault**.

Логичный следующий шаг на столе — **B.4/B.5 с PGOOD**; если LA есть — заодно **PB8** на `RESET_BRIDGE`. После этого голую плату можно считать готовой к установке в систему; полный цикл **E/F/D** — при подключении дисплея и Q7.

Нужна пошаговая инструкция именно для B.4/B.5 (куда щуп, что смотреть в `GET_STATUS` до/после) — напишите, распишу под вашу ревизию.
